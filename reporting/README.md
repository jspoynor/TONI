# Nemo local reporting rules

Working prototype of the structured reporting and validation layer. It makes no network calls and uses no API credits. It does not extract financial fields from OCR text.

## Contract

`Draft` contains a reporting request and evidence for six fields: revenue, cash_on_hand, arr, management_context, risks, help_requested.

- Request: company/request IDs, monthly or quarterly frequency, explicit period start/end, due date, reporting currency, required fields, ARR applicability and a question limit (1-3).
- Field evidence: zero or more candidates, each with value, dates, units, currency and a source reference. Numeric values must be JSON numbers, not formatted strings.
- Source: original file and page or company-answer message ID; an evidence quote/label; an uncertainty flag.
- Resolution: selecting a conflicting candidate requires an explicit company-answer reference. Both original candidates remain in the report.

`draft.schema.json` is the generated JSON Schema for incoming drafts. `reporting.py` also enforces cross-field rules not expressible in that schema. Validate with the Python model as well as the schema.

This is a stricter version of the first sample-kit contract. Narrative candidates now carry the reporting period, and field evidence supports multiple candidates. `build_examples.py` demonstrates migration of the old answer keys. Those inputs are manually curated expected data, not output from an automatic OCR interpreter. Source labels in the migrated fixtures come from the original answer keys; a real adapter should supply exact document excerpts.

## Rules implemented

- No value: missing. A numeric zero remains a valid value.
- Required fields must be present. Optional empty fields do not trigger questions, but optional fields with conflicts or uncertainty still block submission.
- Revenue and narrative must match the requested period. Cash and ARR must match the requested period-end date. Out-of-period candidates remain available as evidence but cannot populate the report value.
- Financial currency must match the request. Missing currency and units cause clarification. No currency conversion or guessed scaling is performed. Inputs in thousands/millions must be explicitly normalized by a later adapter, retaining original evidence.
- ARR requires its definition. No annualization of revenue is performed. A request explicitly configured with ARR not applicable can omit it. Providing ARR while configured not applicable triggers clarification.
- Numeric fields reject strings, booleans, NaN and infinity. Blank narratives are unresolved; an explicit “none” is accepted.
- Differing candidate values or metadata trigger conflict. Selecting one requires company evidence. Identical duplicates preserve their sources.
- OCR uncertainty flags block acceptance. The adapter must set this flag; these rules cannot detect every OCR mistake.
- At most three fixed questions per turn. Conflicts first, then unclear dates/units, missing financials, and narrative gaps. Re-evaluate after each structured answer to remove resolved fields from the queue.
- No explanations are fabricated or inferred from trends. Questions are fixed templates, not generated by a model.
- Company/request IDs must match. This prevents accidental mixing in a payload; it is not user authentication or access control.

## State flow

`needs_information` -> `ready_for_review` -> explicit company confirmation -> `submitted`

`validate(draft)` is pure: it returns a new report view with field states and questions, without modifying the input or confirming anything.

`review_hash(draft)` identifies the exact draft shown in a review. `submit(...)` refuses unresolved reports, missing confirmation or a draft that changed after review. It returns a detached JSON string with a timestamp, version and confirmed fields. Edits to the draft cannot mutate that string.

The surrounding application must authenticate the confirmer, save the snapshot as a new immutable version, assign unique version numbers, handle concurrent edits and connect submission to the UI. This prototype does not implement storage, authentication, email, automatic recurrence, or audit-grade tamper protection. A hash protects against stale review in an honest application flow; it is not a signature or authorization mechanism.

## Run

Python 3.10+ and Pydantic 2 are required. The tested version is pinned in requirements.txt.

```bash
python -m pip install -r requirements.txt
python reporting.py examples/missing_input.json --output missing_result.json
python -m unittest discover -s . -v
```

Example Python usage:

```python
import json
from reporting import Draft, validate, review_hash, submit

draft = Draft.model_validate_json(open('examples/complete_input.json').read())
preview = validate(draft)
reviewed = review_hash(draft)  # Store with the exact preview the company sees.
# Only after an authenticated company user actually confirms that preview:
snapshot = submit(draft, reviewed_hash=reviewed,
                  confirmed_by='authenticated-user-id',
                  company_confirmed=True, version=1)
```

Never run `submit` automatically after extraction. `examples/submitted_demo.json` is explicitly a simulated confirmation, not a real company submission.

## Files and handoff

- `reporting.py`: models, validation, question queue, review hash and snapshot creation.
- `draft.schema.json`: incoming JSON contract for Jackson's UI and the future model adapter.
- `examples/*_input.json`: structured inputs for complete, missing, conflicting, wrong-period and resolved cases.
- `examples/*_report.json`: actual rules-engine output for each input.
- `REPORT_DEMO.md`: readable views of these results.
- `test_reporting.py`: 22 behavioral tests, including missing data, currency/units, zero values, scope, uncertainty, monthly/quarterly requests, conflicts, confirmation and stale drafts.
- `build_examples.py`: regenerates fixtures from the sibling `sample-data/developer` directory. It needs that original kit; the main engine/tests run with included examples.

The original complete/scanned document pair represents the same semantic fixture. Both local extraction formats will ultimately feed this same structured contract. This run tests that contract, not whether a model correctly maps either text output into it.

## Decisions still needed before integration

The application supplies explicit period boundaries; the engine does not calculate or enforce fiscal calendars or recurrence schedules. Whether a different cash as-of date is acceptable is a product policy: this starter requires period end. Real customer requirements may need different rules.

Next: connect Jackson's UI to these fixtures, then build an OCR-text-to-candidate adapter using the OpenAI API and evaluate its outputs against the answer keys. The rule engine remains the validation layer after that adapter. Do not feed expected answers to the model during evaluation.
